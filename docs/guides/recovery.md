# Sealed accounts, and getting one back

*Replaces `mpc.md`, which documented the threshold-signature package deleted on
2026-09-22. If you are looking for GG18, safe primes, or a signing party, they
are gone and the last section of this page says what happened to them.*

An account on this chain is an ordinary secp256k1 key. The person who holds it
signs with it, alone, and nothing co-signs. This guide is about the other
half — what happens when they lose the device holding it.

---

## The one-sentence version

The key is **sealed under the account holder's password and only then split
three ways**: one part on the device, one with the custodian service, one with
the recovery service. Any two parts plus the password rebuild it.

The order is the entire design. Split the raw key instead and the custodian and
the recovery service — both run by the platform — reconstruct it between them.
"No single service can move your money" would then be true while "not even both
of them together can" was false, and the second is the one that matters when one
operator runs both.

---

## What each party holds

| Party | Holds | Can it sign? | Can it open the seal? |
| --- | --- | --- | --- |
| Device | The key itself, plus one part | **Yes, alone** | It has the password |
| Custodian | One part of the ciphertext | No | No |
| Recovery | One part of the ciphertext | No | No |

A part on its own is **information-theoretically nothing**: every possible
ciphertext remains exactly as likely as it was before. That is what separates
Shamir sharing from an encoding, and it is why the device's part is stored in
plain `localStorage` rather than encrypted — see
`clients/wallet/src/account/stored.ts`, which argues the point.

---

## What it costs, and what it does not defend

**One breached service leaks nothing.** Not a key, not a ciphertext, not
anything a password can be tested against. A single part carries no
authentication tag, so there is no oracle to grind.

**Both services breached exposes the account to offline password guessing**, at
Argon2id cost. The threshold scheme offered no such avenue, and this is a real
reduction rather than a wash. It is the trade the architecture already made
elsewhere: nothing co-signs and nothing can freeze a payment, so a stolen device
and password is a stolen account regardless of what this file does.

The length floor in `checkPassword` is what makes the second clause mean
anything.

## The parameters, and why they are what they are

```
Argon2id    t=3, m=128 MiB, p=1, 32-byte key
seal        XChaCha20-Poly1305, 24-byte random nonce
sharing     Shamir over GF(2^8), 2 of 3
```

Every one of these is constrained by the **browser**, because the device is what
creates a sealed account and whatever the services do must be reproducible in
JavaScript. Three constraints are not negotiable:

- **Parallelism is 1.** libsodium's `crypto_pwhash` exposes no way to change it.
  An earlier version used 4, which no browser could reproduce — so a blob sealed
  by the service could never have been opened by the device that needed it.
- **The salt is exactly 16 bytes.** libsodium throws otherwise, so the domain
  separator is hashed into the salt rather than prepended to it.
- **There is no associated data.** The AEAD `@cosmjs/crypto` exposes takes none.
  Nothing is unbound by that: the domain is inside the Argon2 salt and the cost
  parameters are inputs to the derivation, so a tampered header still fails.

Memory was measured on the same WASM the browser runs, not guessed:

| Parameters | Desktop |
| --- | --- |
| t=24, m=12 MiB — what the wallet vault already ships | 0.49 s |
| **t=3, m=128 MiB — this** | **0.65 s** |
| t=2, m=256 MiB | 0.88 s |
| t=4, m=256 MiB | 1.80 s |

A phone is three to six times slower. 256 MiB was rejected on **memory** rather
than time: a quarter-gigabyte WASM allocation on a low-end Android browser is a
failure cliff, and the difference between 128 and 256 MiB is about one bit of an
attacker's cost beside the entropy of the password itself.

## Three implementations, one set of vectors

The same arithmetic is written three times — `recovery/` in Go,
`clients/wallet/src/account/` in TypeScript, `clients/keys/sharing.js` for the
public demonstrator. That would normally be a bug with a delay fuse on it.

None of them is the reference. All three answer to
**`recovery/testdata/vectors.json`**, generated by Go and read by the other two:

```bash
go test ./recovery -run TestVectors -update-vectors
```

Regenerating is a decision, not a fix. If a vector stops matching and nothing was
deliberately changed about the format, the code is wrong and the vector is right.

The failure this guards is silent and late. Everything looks correct at
enrolment; the disagreement surfaces only when somebody who has lost their phone
tries to get their account back, which is exactly the moment there is no
debugging left to do. Three real incompatibilities were found this way while
writing the browser half, and each had passed its own round-trip test.

## Enrolling

One request per service, `POST /v1/enrol`:

```json
{
  "email": "...", "password": "...",
  "pubkey": "<base64, compressed secp256k1>",
  "holding": { "role": "custodian", "salt": "...", "nonce": "...",
               "time": 3, "memory": 131072, "threads": 1,
               "share": { "x": 2, "y": "..." } },
  "signature": "<base64, 64 bytes r||s>"
}
```

The signature is over
`recovery.DepositDigest(email, role, pubkey, holding)` — length-prefixed, so
fields cannot be re-cut across their boundaries.

**It is signed over the email, not the blind index.** The index is
`HMAC(pepper, email)` and the pepper never leaves the service, so a device could
not compute it. The index stays a storage detail, and it has to: the two
deployments hold different peppers and derive different indexes for one person.

What the signature proves: whoever assembled this deposit held the key, and
meant *this* holding for *this* service for *this* account. What it does not
prove: that the holding decrypts to that key. Nothing can — that needs the
password, and a service able to check would be a service able to grind it. The
residual risk is a broken client filing a well-formed holding of the wrong key,
which costs that person their own account and is not a route to anybody else's.

The address is **derived** from the verified public key, never taken from the
request. There is no address field to lie in.

Enrolment protects the key the wallet already has, so **the address does not
change**.

## Recovering

Operator endpoints, on loopback, in order:

```
POST /v1/recovery/initiate   operator, team, proof   -> the clock starts
POST /v1/recovery/approve    a second operator, a different team
POST /v1/recovery/complete   after 72 hours and two approvals
POST /v1/recovery/cancel     anybody, any time before the holding is released
```

Then the **customer** endpoint, the only one in the service that emits key
material:

```
POST /v1/recovery/claim      email + password + recovery id -> one holding
```

Rules that must not be softened: two approvers from different teams and never
the initiator or their team; 72 hours as a constant; **notice failing aborts the
whole recovery**, and the default notifier refuses, because a service running
the process correctly and silently is the worst configuration it can be in.

### The 24 hours changed meaning, and the name did not

It used to be "access restored, but this account cannot spend for 24 hours",
enforced by the custodian refusing to co-sign. Nothing co-signs now, so that
enforcement is simply gone — the service never sees a payment and could not stop
one.

The only lever left is **when the holding is released**, so the delay moved
there. It is now "you get your account back in 24 hours". Strictly later for the
legitimate holder, and the same daylight for the real owner to notice and
object — which is why a completed recovery can now be cancelled inside that
window. Refusing that would be asking somebody to object to something and giving
them no way to do it.

---

## What went, and why

The decision of 2026-09-18 — *a deal is between a buyer and a seller, and the
services appear only in a recovery* — removed the reason for threshold ECDSA.
GG18 exists so several parties can sign without any of them holding the key, and
that is precisely the property nobody wanted. What remained was putting a lost
key back together, which is secret sharing.

Deleted on 2026-09-22: `mpc/`, `mpc/wasm`, `tools/mpc/`, `spike/dkls23`, the
`github.com/bnb-chain/tss-lib/v2` dependency, and with it the `replace` directive
for the withdrawn `github.com/agl/ed25519`.

Measured, not estimated:

| | Before | After |
| --- | --- | --- |
| Enrolment on a phone | ~9.5 min, needing a Web Worker | one request |
| Enrolment endpoints | 3, with a session store | 1, stateless |
| Shipped to the browser | a 19 MB `mpc.wasm` | nothing |
| `clients/keys` | 19 MB | 141 KB |
| `tools/custodian` | — | 1,253 lines removed |
| Package test time | 148 s | 12 s |
| Third-party crypto dependency | tss-lib | none |

What the old scheme could do and this cannot: refuse a payment. A frozen account
can still spend, and a freeze now blocks a *recovery* instead — a narrower
promise, and the right one to make, because it is the one that can be kept.
